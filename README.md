# المجتمع التعليمي | Educational Community

منصة تعليمية مستقلة لطلاب المرحلة الثانوية في مصر، توفر محتوى تعليميًا منظمًا حسب المرحلة والمسار والمقرر، مع موقع للطلاب وتطبيق Android ولوحة إدارة منفصلة لإدارة المحتوى والامتحانات والاشتراكات والنتائج.

> **هذا المشروع مستقل تمامًا عن منصة المدرسين.** لا توجد مشاركة للحسابات أو قواعد البيانات أو الاشتراكات أو المحتوى أو الإدارة بين المشروعين.

## 1. نظرة عامة

المجتمع التعليمي هو منتج رقمي يقدم تجربة تعليمية مركزية للطلاب. تتولى إدارة المنصة التحكم في الهيكل الدراسي والمحتوى والامتحانات والاشتراكات ومراجعة المدفوعات والتصحيح.

### التطبيقات الرئيسية

1. **Student Web App:** موقع الطالب، مبني باستخدام Next.js، ويحتوي على واجهة الطالب ومسارات `/api` الخاصة بخدمات النظام.
2. **Admin Dashboard:** لوحة إدارة مستقلة، مبنية باستخدام React وVite، ولا تستخدم واجهة الطالب.
3. **Android App:** تطبيق Android للطلاب، مبني باستخدام Expo وReact Native باستخدام Development Build.

تستخدم التطبيقات الثلاثة Backend واحدًا خاصًا بالمجتمع التعليمي. لكل تطبيق واجهته وتجربة استخدامه، بينما تتم مشاركة الهوية والبيانات وقواعد العمل من خلال الخدمات المركزية.

### مبادئ أساسية

- استقلال كامل عن أي منتج آخر.
- الإدارة هي المصدر المعتمد للصفوف والمراحل والمسارات والمقررات والمحتوى والامتحانات المركزية.
- الطالب يختار من الخيارات التي أنشأتها الإدارة؛ ولا ينشئ مراحل أو مسارات أو مقررات بنفسه.
- حساب الطالب نفسه يعمل على الموقع وتطبيق Android.
- الدفع والاشتراكات يتم التعامل معهما من خلال موقع الويب فقط.
- تطبيق Android مخصص لتسجيل الدخول واستخدام المحتوى والخدمات التعليمية، ولا يحتوي على شراء أو دفع أو توجيه إلى الدفع الخارجي.
- فريق الإدارة مسؤول عن إنشاء الامتحانات المركزية وتصحيحها واعتماد نتائجها.
- توقيت النظام المعتمد هو توقيت القاهرة.
- خصائص الذكاء الاصطناعي خارج نطاق الإصدار الأول.

## 2. نطاق المنتج

### داخل نطاق الإصدار الأول

- تسجيل حساب الطالب وتسجيل الدخول واستعادة الوصول إلى الحساب.
- اختيار المرحلة الدراسية والمسار/القسم من الخيارات المنشأة بواسطة الإدارة.
- عرض المقررات المتاحة للطالب حسب مرحلته ومساره.
- مكتبة تعليمية منظمة: مقرر ← وحدات ← دروس.
- عرض الشروحات والمواد التعليمية وملفات PDF.
- أسئلة سريعة مرتبطة بالدروس.
- إنشاء وجدولة الامتحانات المركزية.
- أسئلة اختيار من متعدد وأسئلة مقالية، مع دعم الأسئلة الفرعية عند الحاجة.
- تحديد درجات الأسئلة والتحقق من مجموع الدرجات.
- أداء الطالب للامتحان وفق الموعد والمدة وقواعد المحاولة المعتمدة.
- تصحيح الامتحانات بواسطة فريق الإدارة.
- إخفاء هوية الطالب عن المصحح أثناء عملية التصحيح، ثم إظهارها لصاحب الصلاحية بعد انتهاء التصحيح وفق قواعد الصلاحيات.
- اعتماد النتائج وإتاحتها للطالب.
- إشعارات الامتحانات والتذكيرات.
- اشتراك مجاني لمدة 10 أيام.
- خطط اشتراك مدفوعة وإدارة صلاحية الوصول.
- الدفع من الويب عن طريق التحويل البنكي أو InstaPay أو Vodafone Cash مع مراجعة إدارية يدوية.
- لوحة إدارة منفصلة لإدارة الطلاب والبيانات الأكاديمية والمحتوى والامتحانات والتصحيح والمدفوعات والتقارير.
- تطبيق Android مستقل للطالب.

### خارج نطاق الإصدار الأول

- تطبيق iOS.
- الدفع أو شراء الاشتراك من داخل تطبيق Android.
- توجيه المستخدم من تطبيق Android إلى صفحة دفع خارجية.
- ربط المجتمع التعليمي بمنصة المدرسين أو مشاركة بيانات أو حسابات بينهما.
- أدوات الذكاء الاصطناعي للشرح أو إنشاء الأسئلة أو التصحيح أو التقييم.
- أي تكاملات أو مزايا لم يتم اعتمادها ضمن وثائق المتطلبات.

## 3. هيكل المستودع (Monorepo)

الهيكل المعتمد للمشروع:

```text
community/
├─ apps/
│  ├─ web/        # Next.js: موقع الطالب + مسارات /api
│  ├─ admin/      # React + Vite: لوحة الإدارة
│  └─ mobile/     # Expo (Development Build): تطبيق Android
│
├─ packages/
│  ├─ shared/     # الأنواع، مخططات Zod، رموز الأخطاء والحالات، أدوات توقيت القاهرة
│  └─ api-client/ # عميل API مكتوب الأنواع لمسارات /api (للإدارة والتطبيق)
│
├─ supabase/
│  ├─ migrations/ # الجداول والقيود والعروض والدوال وسياسات RLS
│  ├─ functions/  # Edge Functions، ومنها إرسال Push Notifications
│  ├─ seed/       # البيانات المرجعية الأولية
│  └─ tests/      # اختبارات pgTAP للقيود والصلاحيات وعرض التصحيح
│
├─ docs/          # SRS وUX والمعمارية والقرارات التقنية
└─ .github/
   └─ workflows/ # CI/CD pipelines
```

### مسؤولية كل جزء

| المسار | المسؤولية |
|---|---|
| `apps/web` | واجهة الطالب على الويب، الصفحات العامة والخاصة، ومسارات Backend تحت `/api`. |
| `apps/admin` | لوحة الإدارة المستقلة، وإدارة المحتوى والامتحانات والطلاب والمدفوعات والتقارير. |
| `apps/mobile` | تطبيق Android للطالب باستخدام Expo Development Build. |
| `packages/shared` | العقود المشتركة والأنواع والتحقق من البيانات ورموز الأخطاء والحالات وأدوات الوقت. |
| `packages/api-client` | عميل موحد ومكتوب الأنواع للتواصل مع `/api` من لوحة الإدارة وتطبيق Android. |
| `supabase/migrations` | تغييرات قاعدة البيانات المحفوظة كتاريخ migrations قابل للمراجعة وإعادة التطبيق. |
| `supabase/functions` | الوظائف الطرفية التي تحتاج تشغيلًا على Supabase، مثل إرسال الإشعارات. |
| `supabase/seed` | البيانات المرجعية اللازمة للبيئات الجديدة والاختبارات. |
| `supabase/tests` | اختبارات قاعدة البيانات والصلاحيات والقيود. |
| `docs` | مواصفات المتطلبات والتصميم وتجارب المستخدم والقرارات المعمارية. |
| `.github/workflows` | فحوصات الجودة والبناء والاختبارات والنشر الآلي. |

## 4. التقنيات المعتمدة

| الطبقة | التقنية | الاستخدام |
|---|---|---|
| Student Web | Next.js + React + TypeScript | موقع الطالب ومسارات `/api`. |

| Shared Types | TypeScript | العقود والأنواع المشتركة بين التطبيقات. |
| API Client | Typed API Client | استدعاء مسارات `/api` من الإدارة والموبايل. |

| Styling Mobile | NativeWind أو إعداد Native مناسب | تنسيق تطبيق React Native مع مراعاة اختلاف مكونات Native عن HTML. |
| Server State | TanStack Query | جلب بيانات الخادم وإدارتها في الكاش. |
| Client State | Zustand | حالة الواجهة المحلية فقط. |
| Web Forms | React Hook Form | إدارة النماذج. |
| Web UI | shadcn/ui ومكونات مخصصة | مكونات لوحة الإدارة وموقع الطالب. |
| Unit Tests | Vitest | اختبارات المنطق والوحدات. |
| Component Tests | React Testing Library | اختبار سلوك مكونات React. |
| Web E2E | Playwright | اختبارات رحلات المستخدم على الويب. |
| Mobile E2E | Maestro | اختبارات التطبيق على Android. |
| Database Tests | pgTAP | اختبار القيود والصلاحيات والدوال وسياسات قاعدة البيانات. |
| Load Testing | k6 عند الحاجة | اختبار الأداء والحمل المتزامن. |

> ملاحظة: اختيار إصدارات الحزم النهائية وأوامر التشغيل والنشر يتم تثبيته في ملفات إعداد المشروع عند بدء التهيئة. لا تُستخدم إصدارات تجريبية في Production دون قرار موثق.

## 5. نموذج الاستخدام والأدوار

### الطالب

يستطيع الطالب:

- إنشاء حساب وتسجيل الدخول من الويب أو Android.
- استخدام نفس بيانات الحساب على التطبيقين.
- تحديد المرحلة والمسار من الخيارات المتاحة.
- تصفح المقررات المتاحة له.
- فتح الوحدات والدروس والشروحات وملفات PDF.
- الإجابة عن الأسئلة السريعة.
- الاطلاع على الامتحانات المجدولة والمتاحة له.
- أداء الامتحان وفق قواعد المحاولة والوقت.
- متابعة حالة التصحيح والنتائج بعد إتاحتها.
- متابعة حالة الاشتراك وصلاحية الوصول.

### الإدارة وفريق التشغيل

تتولى الإدارة:

- إنشاء وإدارة حسابات الإدارة حسب الصلاحيات الداخلية.
- إدارة المحافظات والبيانات المرجعية اللازمة عند التسجيل.
- إنشاء المراحل والصفوف والمسارات/الأقسام والمقررات.
- إدارة الطلاب وحالات الحساب والوصول.
- إنشاء الوحدات والدروس وإضافة الشروحات والملفات والأسئلة السريعة.
- إنشاء الامتحانات المركزية وجدولتها وتحديد الطلاب المستهدفين.
- متابعة المحاولات والإجابات.
- تصحيح الأسئلة المقالية وإدارة عملية التصحيح.
- مراجعة الإجابات الموضوعية وفق نموذج الإجابة المعتمد.
- اعتماد النتائج وإتاحتها.
- إدارة الخطط والأسعار والاشتراكات.
- مراجعة إثباتات الدفع وتفعيل الاشتراكات أو تمديدها.
- إدارة الإشعارات والتذكيرات.
- متابعة التقارير وسجل العمليات.

> يمكن فصل صلاحيات أعضاء فريق الإدارة إلى أدوار مثل مدير، محرر محتوى، مسؤول امتحانات، ومصحح. تفاصيل هذه الأدوار النهائية تُوثق في SRS ومصفوفة الصلاحيات، ولا يُفترض أن كل موظف يمتلك جميع الصلاحيات.

## 6. الهيكل الأكاديمي والمحتوى

### الهيكل الأكاديمي

الهيكل ينشأ مركزيًا بواسطة الإدارة. الطالب لا يضيف أو يعدل عناصره.

```text
المحافظة (عند الحاجة في بيانات الطالب)
└── المرحلة / الصف الدراسي
    └── المسار أو القسم
        └── المقرر
            └── الوحدة
                └── الدرس
                    ├── شرح أو محتوى تعليمي
                    ├── ملفات PDF
                    └── أسئلة سريعة
```

### قواعد إدارة الهيكل

- الإدارة هي المسؤولة عن تعريف المراحل والصفوف.
- الإدارة هي المسؤولة عن تعريف المسارات والأقسام، بما فيها المسارات الجديدة التي قد تظهر في النظام التعليمي المصري.
- الإدارة تربط المقررات بالمراحل والمسارات المناسبة.
- الطالب يختار من القيم المنشأة مسبقًا فقط.
- يجب أن يكون إظهار المقررات للطالب متوافقًا مع مرحلته ومساره.
- تعديلات الهيكل الأكاديمي يجب ألا تؤدي إلى فقدان أو كسر المحتوى أو النتائج التاريخية المرتبطة به.

### إدارة المحتوى

- إنشاء مقرر وتحديد اسمه ووصفه وصورته التعريفية عند الحاجة.
- إنشاء وحدات داخل المقرر.
- إنشاء دروس داخل الوحدة.
- ترتيب الوحدات والدروس والتحكم في ظهورها.
- إضافة نصوص أو شروحات تعليمية.
- رفع وإدارة ملفات PDF.
- إضافة أسئلة سريعة للدرس.
- معاينة المحتوى قبل نشره.
- نشر المحتوى أو إخفاؤه وفق صلاحيات الإدارة.

## 7. الامتحانات المركزية والتصحيح

### إنشاء الامتحان

الإدارة هي الجهة المسؤولة عن إنشاء الامتحانات المركزية. تشمل إعدادات الامتحان، وفق المتطلبات المعتمدة:

- اسم الامتحان ووصفه.
- المرحلة والمسار والمقرر المستهدف.
- تاريخ ووقت البدء.
- مدة الامتحان.
- الدرجة النهائية.
- الأسئلة وأنواعها.
- درجة كل سؤال، ودرجات الأسئلة الفرعية عند وجودها.
- نموذج الإجابة للأسئلة الموضوعية.
- إعدادات المحاولة والنتيجة.

### أنواع الأسئلة

- اختيار من متعدد (MCQ).
- أسئلة مقالية.
- سؤال رئيسي يحتوي على مجموعة أسئلة فرعية، مثل أسئلة القطعة.

### قواعد الدرجات

- يحدد منشئ الامتحان الدرجة المخصصة لكل سؤال.
- يجب أن يساوي مجموع درجات الأسئلة الدرجة النهائية للامتحان قبل نشره.
- يجب التحقق من درجات الأسئلة الفرعية وعدم احتسابها مرتين.
- يجب منع نشر امتحان غير مكتمل أو غير صالح وفق قواعد التحقق.

### الجدولة والإتاحة

- يتم تحديد تاريخ ووقت الامتحان بواسطة الإدارة.
- لا يظهر الامتحان للبدء قبل الموعد المحدد.
- يغلق الامتحان عند انتهاء مدته وفق قواعد التسليم المعتمدة.
- يتم إرسال إشعار قبل الامتحان بأسبوع، ثم تذكيرات يومية حتى موعده وفق سياسة الإشعارات.
- يعتمد النظام توقيت القاهرة في العرض والجدولة.

### المحاولات وحفظ الإجابات

- قواعد عدد المحاولات تُطبق كما هي معتمدة في SRS.
- يجب تسجيل بداية المحاولة ووقت انتهائها وحالتها.
- يجب حفظ الإجابات بطريقة تتحمل انقطاع الاتصال قدر الإمكان.
- يجب ألا يعتمد النظام على ساعة جهاز الطالب كمصدر موثوق لوقت الامتحان.
- يجب تسجيل حالات الانقطاع والاستعادة والتسليم والأخطاء المهمة.

> مهلة إعادة الاتصال البالغة خمس دقائق وكون وقت الامتحان مستمرًا أثناء الانقطاع وردا في قرارات التحليل السابقة. يجب تثبيت التفاصيل التنفيذية الدقيقة للتسليم التلقائي والإجابات التي تم حفظها في مواصفات الامتحانات قبل التنفيذ.

### التصحيح والنتائج

- فريق الإدارة هو المسؤول عن تصحيح الامتحانات المركزية.
- يجب إخفاء هوية الطالب عن المصحح أثناء التصحيح.
- بعد انتهاء التصحيح، تظهر الهوية لصاحب الصلاحية وفق قواعد الوصول.
- تعتمد النتيجة ويجري قفلها بعد اعتماد المصحح/صاحب الصلاحية المحدد.
- النتيجة المعتمدة لا تعدل وفق القرار الحالي، وأي استثناء إداري يجب أن يكون قرارًا موثقًا قبل إضافته إلى النظام.
- تظهر النتيجة للطالب بعد اعتمادها وإتاحتها.

## 8. الاشتراكات والمدفوعات

### الفترة المجانية

- يحصل الطالب على فترة مجانية مدتها 10 أيام.
- يجب تسجيل بداية الفترة المجانية ونهايتها وحالة الاستفادة منها.
- ضوابط منع تكرار التجربة عند إنشاء حسابات متعددة يجب تثبيتها في مواصفات الاشتراكات.

### الاشتراكات المدفوعة

- الإدارة تحدد خطط الاشتراك والأسعار والمدد.
- يمكن أن تشمل الخطط شهرًا أو ترمًا أو سنة دراسية وفق الخطط التي تنشئها الإدارة.
- يتم تحديد بداية ونهاية صلاحية الاشتراك بوضوح.
- صلاحية الوصول للمحتوى تعتمد على حالة الاشتراك المعتمدة، وليس على بيانات الواجهة وحدها.

### الدفع من الويب فقط

طرق الدفع المقررة:

- تحويل بنكي.
- InstaPay.
- Vodafone Cash.

تدفق الدفع المبدئي:

1. الطالب يسجل الدخول إلى موقع الويب.
2. يختار خطة الاشتراك المناسبة.
3. يرسل إثبات الدفع والبيانات المطلوبة.
4. يظهر الطلب للإدارة بحالة انتظار المراجعة.
5. تراجع الإدارة المبلغ والإثبات.
6. تقبل الإدارة الطلب أو ترفضه مع تسجيل السبب عند الرفض.
7. عند القبول، يتم تفعيل الاشتراك وتحديد فترة الوصول.
8. تظهر الحالة الجديدة للطالب على الويب وتطبيق Android.

### سياسة تطبيق Android

تطبيق Android:

- لا يعرض أسعار أو خطط شراء.
- لا يحتوي على عملية دفع.
- لا يحتوي على زر شراء أو رابط دفع خارجي.
- لا يوجه الطالب إلى موقع الويب بغرض إتمام عملية شراء.
- يسمح للطالب بتسجيل الدخول واستهلاك المحتوى الذي يحق له الوصول إليه.
- يعرض حالة الوصول أو عدم الإتاحة برسالة محايدة ومناسبة.

يجب مراجعة سياسة Google Play السارية وقت النشر، وتوفير بيانات اختبار وتعليمات واضحة لمراجعي التطبيق عند الحاجة.

## 9. المصادقة والصلاحيات والأمان

### الهوية وتسجيل الدخول

- حساب الطالب واحد للاستخدام على Student Web وAndroid.
- لوحة الإدارة منفصلة في الواجهة ومسار الاستخدام.
- إنشاء حسابات الإدارة يتم عبر إجراء إداري محمي، وليس من التسجيل العام للطلاب.
- يجب دعم تسجيل الخروج وإدارة الجلسات واستعادة الحساب وفق متطلبات SRS.

### قواعد أمنية إلزامية

- لا يتم اعتبار إخفاء زر في الواجهة بديلًا عن التحقق من الصلاحية على الخادم.
- كل عملية محمية يجب أن تتحقق من هوية المستخدم وصلاحيته على الخادم.
- تفعيل Row Level Security على الجداول المكشوفة حسب الحاجة.
- عدم وضع مفاتيح `service_role` أو الأسرار في تطبيقات الويب أو الموبايل.
- عدم الوثوق في الدور أو السعر أو الدرجة أو حالة الاشتراك المرسلة من العميل دون تحقق.
- تسجيل العمليات الإدارية الحساسة في سجل تدقيق.
- تقييد تنزيل الملفات التعليمية بحسب صلاحية الطالب.
- حماية مسارات إدارة المحتوى والامتحانات والتصحيح والمدفوعات.
- عدم إظهار هوية الطالب للمصحح أثناء مرحلة التصحيح.

### خصوصية الطلاب

- جمع أقل قدر ممكن من البيانات الشخصية اللازمة لتشغيل الخدمة.
- تقييد الوصول إلى بيانات الطالب حسب الدور والغرض.
- حماية بيانات تسجيل الدخول والجلسات وإثباتات الدفع والنتائج.
- تحديد سياسة الاحتفاظ بالبيانات والحذف والتصدير ضمن وثائق المنتج والسياسات القانونية.
- عدم إرسال معلومات شخصية أو إجابات امتحانات ضمن سجلات التحليلات غير الضرورية.

## 10. إدارة الحالة والكاش والأداء

### مبدأ عام

يجب تقليل الطلبات والبيانات المنقولة دون التضحية بصحة بيانات الامتحانات والاشتراكات والنتائج.

### قواعد مقترحة

- استخدام TanStack Query لإدارة Server State والكاش وإعادة الجلب.
- استخدام Zustand لحالة الواجهة المحلية فقط.
- عدم تخزين نسخة ثانية من نفس Server State داخل Zustand.
- استخدام Pagination أو Infinite Queries للقوائم الطويلة.
- طلب الأعمدة والحقول اللازمة فقط بدل جلب السجل بالكامل.
- استخدام Database Indexes بما يتوافق مع الاستعلامات الفعلية.
- استخدام CDN وHTTP caching للملفات العامة أو القابلة للتخزين المؤقت حسب الصلاحيات.
- استخدام روابط موقعة أو مسارات آمنة للملفات الخاصة.
- عدم الاعتماد على بيانات مخزنة مؤقتًا كمرجع نهائي لصلاحية الاشتراك أو صلاحية دخول الامتحان.
- إعادة التحقق من الحالة عند تنفيذ عملية حساسة مثل بدء الامتحان أو تسليم الإجابات أو عرض النتيجة.
- تحديد سياسات cache invalidation عند تعديل المحتوى أو البيانات الأكاديمية أو الاشتراكات.

### بيانات لا يجب التعامل معها كبيانات ثابتة

- حالة الاشتراك.
- أهلية الطالب لدخول امتحان.
- وقت بداية ونهاية الامتحان.
- حالة المحاولة.
- حالة اعتماد النتيجة.
- صلاحيات الإدارة.

## 13. الاختبارات وضمان الجودة

الاختبارات جزء من عملية التطوير، وليست خطوة نهائية بعد اكتمال البرمجة.

### أنواع الاختبارات

| النوع | الأداة المقترحة | الغرض |
|---|---|---|
| Unit Tests | Vitest | اختبار قواعد العمل والدوال المنفصلة. |
| Component Tests | React Testing Library | اختبار تفاعل المستخدم مع المكونات. |
| API Integration | Vitest أو أداة HTTP مناسبة | اختبار مسارات `/api` مع بيئة اختبار. |
| Database Tests | pgTAP | اختبار القيود والدوال وسياسات RLS. |
| Web E2E | Playwright | اختبار رحلات الطالب والإدارة كاملة. |
| Android E2E | Maestro | اختبار رحلات التطبيق على Android. |
| Load Tests | k6 | اختبار ضغط الامتحانات وتزامن الطلاب عند الحاجة. |

### سيناريوهات لا بد من اختبارها

- الطالب لا يستطيع رؤية بيانات طالب آخر.
- الطالب لا يستطيع الوصول إلى محتوى غير متاح لاشتراكه.
- التطبيق لا يعرض أي خيار دفع أو رابط دفع خارجي.
- اعتماد الدفع يفعّل الوصول الصحيح على الويب وAndroid.
- الطالب لا يستطيع بدء امتحان قبل موعده.
- الطالب لا يستطيع إنشاء محاولة إضافية إذا كانت المحاولات مستنفدة.
- انتهاء وقت الامتحان يؤدي إلى السلوك المعتمد للتسليم.
- انقطاع الاتصال واستعادته لا يؤديان إلى فقدان أو تكرار غير صحيح للإجابات المحفوظة.
- مجموع درجات الأسئلة يساوي الدرجة النهائية قبل نشر الامتحان.
- المصحح لا يرى هوية الطالب أثناء التصحيح.
- النتيجة لا تظهر قبل اعتمادها إذا كانت هذه هي سياسة النشر المعتمدة.
- المستخدم غير المخول لا يستطيع إنشاء أو تعديل محتوى أو امتحان.
- ملفات PDF الخاصة لا يمكن تنزيلها من مستخدم غير مخول.
- التذكيرات لا تُرسل مكررًا.
- جميع مواعيد الامتحانات والإشعارات تتوافق مع توقيت القاهرة.

## 14. CI/CD وبيئات التشغيل

### البيئات

- **Local:** تطوير واختبار على جهاز المطور.

يفضل فصل مشاريع Supabase ومفاتيح البيئة والبيانات لكل بيئة، وعدم استخدام بيانات Production في الاختبارات.

### Pull Request Pipeline

ينبغي أن يشمل خط CI المبدئي:

1. تثبيت Dependencies باستخدام lockfile.
2. Formatting وLint.
3. TypeScript Type Check.
4. Unit Tests.
5. Component Tests.
6. تشغيل Supabase المحلي وتطبيق Migrations.
7. اختبارات pgTAP وRLS.
8. Build لتطبيقات الويب.
9. اختبارات API Integration.
10. اختبارات Playwright الأساسية عند توفر بيئة مناسبة.

### النشر

- نشر نسخة Preview أو Staging قبل Production.
- تشغيل Migrations بطريقة منظمة وقابلة للمراجعة.
- عدم تنفيذ تغييرات يدوية غير مسجلة على قاعدة بيانات Production.
- حماية أسرار النشر في GitHub Secrets أو نظام أسرار معتمد.
- جعل النشر إلى Production محكومًا بموافقة أو بوابة حماية.
- بناء Android من خلال EAS مع فصل Development وPreview وProduction profiles.
- الاحتفاظ بسجل للإصدارات وإمكانية الرجوع عن إصدار التطبيق أو الويب عند وجود مشكلة.

## 19. قرارات تحتاج تثبيتًا تفصيليًا قبل التنفيذ

13. مزود البريد أو الرسائل أو Push النهائي وحدود كل قناة.
14. خطة النسخ الاحتياطي والاستعادة ومدة الاحتفاظ بالنسخ.
